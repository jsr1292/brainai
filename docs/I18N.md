# Translating BrainAI

The dashboard speaks English and Spanish (Spain). English is the source; the design is in
`docs/superpowers/specs/2026-11-19-spanish-design.md`.

## How a screen picks its language

One middleware (`src/web/locale.ts`, early in `createApp`) sets the language of each request: the owner's choice in
Settings › Language (`ui_language` in `brain_switches`: `auto`, `en` or `es`) wins; `auto` follows `Accept-Language`
(`es` or `es-*` ranked first among English and Spanish gives Spanish); otherwise English. Anything rendered outside a
request (tests, background work) is English. Views never pass a language around: they call `t()`.

**Machine endpoints stay English.** `/mcp`, `/token`, `/register`, `/revoke`, `/.well-known/*`, `/app/ticket`,
`/app/hello`, `/app/bridge-hello`, `/app/open`, `/app/backup-now`, `/api/*`, `/images*`, `/static/*`, `/sw.js`, `/favicon.ico` run under
`runWithLocale('en')` whatever the owner chose (`isMachinePath` in `src/web/locale.ts`). `/authorize` and the consent page are
for the owner and are localised. `/models/progress` (polled by the page, shows text) stays localised. A new endpoint that talks to a program, not a person, goes into that list.

**Never `t()` text that is persisted (database rows, status files, activity reasons, history) or sent to assistants (MCP
replies, tool descriptions, server instructions, hook and setup texts an assistant reads).** Stored text is English; the
screen that shows it may translate a *label* around it, never rewrite it. A stored value that a screen shows in words (an
activity reason, a status) is stored as a code or in English and mapped to a key at render.

In local mode the choice is also written to `<data folder>/ui-language.json` (`{"language":"auto|en|es","updatedAt":…}`)
for the desktop shell to read at start (stage S3). It is written once when the app starts (from the stored switch) and again
on each change, through a uniquely named temporary file.

### The system language (desktop app, stage S3)

On macOS the desktop WebView follows the app bundle's localisations and sends `Accept-Language: en-US` even on a Spanish Mac.
So in **local mode**, when the choice is `auto` and the environment variable `BRAINAI_SYSTEM_LOCALE` is set (`es-ES`, `es_ES`,
`en-GB`…), that value decides before `Accept-Language`; a language we do not have (`fr-FR`) falls through to the header. A stored
`en` or `es` always wins, and a server ignores the variable. **S3 (the shell) must pass the operating system's preferred
language in `BRAINAI_SYSTEM_LOCALE` when it starts the server.** `desktop/src-tauri/Info.plist` adds
`CFBundleLocalizations` `[en, es]`.

### The desktop shell and the installer (stage S3, done)

- **System language to the server.** `server::env` takes the OS language from the `sys-locale` crate (`es-ES`) and passes it
  as `BRAINAI_SYSTEM_LOCALE` (left out when the OS says nothing).
- **The shell's own texts** are all in `desktop/src-tauri/src/lang.rs`: one `TABLE` of `(key, en, es)` and `tr(key)` /
  `tr_with(key, &[("name", value)])`. That covers the tray menu (Abrir BrainAI, Iniciar al arrancar, Salir de BrainAI, the
  update item), the folder picker title, the remove / move-out / port / crash / start-up dialogs and the update notices
  (`problem_text`, the "move to Applications" and "not writable" sentences, which are written to `update.json` in the
  language in use when the update runs). The English sentences are unchanged. The short fallback `The check failed.` in
  `update-check.json` stays English (stored text). A test checks every key has both languages and the same `{placeholders}`.
- **Which language the shell uses.** The owner's choice in `<data folder>/ui-language.json` (the folder the server's
  `DATA_DIR` points to) wins; `auto`, a missing file, a broken file or an unknown value follows the OS: `es`, `es-*` or `es_*`
  is Spanish, anything else English. It is read at start, every 4 seconds (the tray menu items are re-titled when it changes) and
  each time a dialog flow starts, so changing Settings › Idioma is picked up without restarting.
- **Installer.** `tauri.windows.conf.json` › `bundle.windows.nsis.languages: ["English", "Spanish"]`, with
  `displayLanguageSelector: false`, so the NSIS installer and uninstaller follow the Windows display language and fall back to
  English (the first in the list). Reference: Tauri v2 config schema (`@tauri-apps/cli/config.schema.json`, `NsisConfig`):
  "By default the OS language is used. If the OS language is not in the list of languages, the first language will be
  used." The bundler ships its own Spanish strings for its messages; `windows/hooks.nsh` shows no text. The DMG config has no
  volume name or background text (it is named after the app), so nothing to translate.
- **Info.plist, verified.** The schema says Tauri merges an `Info.plist` next to `tauri.conf.json`. A debug
  `tauri build --debug --bundles app --no-sign` (20 s) gave a `BrainAI.app` whose `Contents/Info.plist` has
  `CFBundleLocalizations = [en, es]` (`plutil -p`).

How to test on a Spanish machine: on a Spanish Mac (System Settings › General › Language & Region, Spanish first) open the
app with the language set to Automático: the menu bar item says Abrir BrainAI / Iniciar al arrancar / Salir de BrainAI, and the
window's pages are Spanish. Choose English in Ajustes › Idioma: the menu follows within a few seconds. On Windows, install with
the display language Spanish: the installer is in Spanish; with another language it is English. Quick check without the OS:
write `{"language":"es"}` in a test data folder's `ui-language.json`. Unit tests: `cargo test` in `desktop/src-tauri`.

## Adding a key

Catalogs are one file per area, English first: `src/i18n/en/<area>.ts`, then `src/i18n/es/<area>.ts` (typed so a missing
key is a compile error). **Every area already has its two files and its line in both index files: never edit `index.ts`.**
A key defined in two area files is a test failure (the area sizes must add up to the merged catalog).

```ts
// en/inbox.ts
export const inbox = { 'inbox.approve': 'Approve', 'inbox.waiting': { one: '{count} waiting', other: '{count} waiting' } } as const;
// es/inbox.ts
export const inbox_es: Record<keyof typeof inbox, Entry> = { 'inbox.approve': 'Aprobar', 'inbox.waiting': { one: '{count} pendiente', other: '{count} pendientes' } };
```

Template, before and after:

```ts
html`<button>Approve</button>`            // before
html`<button>${t('inbox.approve')}</button>`  // after
```

- Keys are short and dotted, prefixed by the area. Params are named: `t('inbox.waiting', { count: n })`.
- **Plurals.** Only a key whose entry is an object (`one`, `other`, and `zero`, `two`, `few`, `many` if the language has them)
  picks a form with `Intl.PluralRules` (one instance per language, cached). A plain string with `{count}` is just filled in: it
  never changes form. The decision: English may keep a plain `'{count} waiting'` string while Spanish gives a plural object
  (`{ one: '{count} pendiente', other: '{count} pendientes' }`); the parity test accepts that when the placeholders match (a
  plural object in English with a plain Spanish string is not accepted). Write English as a plural object when its own forms
  differ (`1 day late` / `2 days late`). Rules for `count`: pass it as a **number**, not a string (a string cannot pick a form);
  **one count per plural key** (a sentence with two counts is two keys, or a sentence with two `{count}`-free params); and do
  not format it: `{count}` is filled with the plain number, no thousands separator. For a grouped number use `fmt.number`
  as a separate param.
- Catalogs hold plain text. The `html` tag escapes it. A sentence with a link or bold word: put `{link}` in the text and use
  `tHtml('x.sentence', { link: html`<a href="/y">${t('x.link')}</a>` })`. Never put HTML in a catalog.
- For a key held in a variable (a table of labels) use `tKey(key)`.
- Dates, sizes, numbers: `fmt.date`, `fmt.dateTime`, `fmt.size`, `fmt.number` (`src/i18n/fmt.ts`); relative times
  (`when.ts`: `pastLabel`, `dueLabel`, `timeAgo`) and `localParts`/`shortDay`/`dayWithWeekday` (`src/timezone.ts`) already follow
  the language. `fmt.size` prints exactly what English always printed (whole KB under 1 MB, otherwise MB with one decimal,
  `1536.0 MB`, no thousands separator, never GB); Spanish only swaps the decimal comma (`1,5 MB`). `formatBytes` in
  `src/diskSpace.ts` (decimal units, `1.4 GB`, "less than 1 KB") is a separate function with its own English output: the
  settings area routes its decimal separator and its words through the catalog when it converts `spaceViews`.
- **Behaviour never reads translated text.** `page()` no longer looks at its title; the lit tab, the lit side place, the back
  link and the crumb come from options the route passes (`tab`, `sideTab`, `back`, `crumb`). `dashboardRoutes`' `send` takes an
  explicit kind (`'settings' | 'facts' | 'fact' | 'newFact' | 'notFound' | 'badRequest'`) next to the title. Other routes'
  local `send` helpers that still compare titles (`pageRoutes`, `discussionRoutes`, `importRoutes`, `skillRoutes`,
  `reviewRoutes`) are converted the same way by the area that owns the file, before its title is translated.
- **Back links** (`src/web/back.ts`): a `Back` / `BackTarget` is `{ href, labelKey?, labelParams?, label? }`. `labelKey` is a
  catalog key translated by `backLabel()` when the page is drawn (`labelParams` may be a function, so a month is worked out at
  draw time); `label` is plain text that is never translated, for a record's own name (a project, a page title). Existing
  `{ href, label: 'Settings' }` literals still work and are converted to `labelKey` as their area is.
- **The Ctrl-K palette** (`setGoTo` in `app.ts`): rows are `{ key, params?, href, alias? }`, translated when the page is drawn.
  `alias` is extra search words, kept as written (English aliases stay useful to someone typing English).
- **Errors from the memory layer.** A `MemoryError` keeps its English `.message` (assistants read it through MCP) and may carry
  `key` and `params` (4th constructor argument `{ key, params }`). Routes show `errorText(e)` (`src/web/errorText.ts`): the
  translated key when there is one, else the message. Converted so far: the secret refusal, the keys refusals and "This list
  changed"; convert others as their dashboard screen is converted, adding the key to `common`. Never use `errorText` for text
  that is stored or sent to an assistant.
- **Other errors people see.** `PageError`, `NoteError`, `ProjectError`, `LearningError`, `TidyError`, `SkillError` and `FileRefused`
  extend `SayableError` (`src/i18n/errors.ts`), and the discussions service throws `MemoryError`s with a key: all keep the English
  `.message` and take a trailing `{ key, params }`. Keys live in `src/i18n/{en,es}/err*.ts` (`err.page.*`, `err.project.*`, ...).
  Screens show `errorText(e)`. Other service text shown on screen has a keyed twin: `backupHealth().say` (`backupProblems()`),
  `Reason.say` in health (`reasonLine()`), `activityWhyCode`, `HomeSuggestion.state/weeks`, `PanelDiscussion.round/waitingFor/closedAt`,
  `ReviewView.sentenceFacts/soFar` and the quiet rows' `state/stateAt`; `reasonText()` words the stored held-save reasons.
- **Reasons, dates and limits in a keyed error.** `errorText(e)` words a `reason` param (a secret kind such as `API key`, or an instruction-like
  reason) through `reasonText`, and a numeric `max` of the limits that always grouped digits (`GROUPED_MAX`) with `fmt.number`: services pass
  the plain number, never `toLocaleString`. A stored "2 Nov 2026" in a held reason is parsed and formatted by `reasonText`.
- **Machine paths with text people see.** `POST /images` is an API (always English) and answers `{ error, code }`; `editor-pics.js` words each
  `code` with a `client.pics.err.<code>` key. The placeholder description of a new picture (`Describe the picture`) is stored Markdown and stays English.
- **Scripts never compare translated words.** The server marks what a script needs to know (`data-back="discussions"` on a back link, from
  `mark` in `BackTarget`); `desk.js` reads the mark.
- **This Mac / this computer.** `computerName()` / `ComputerName()` (`src/desktop/computer.ts`) say it in the request's language;
  `thisComputer()` stays English for anything stored or sent to an assistant.
- **Tests that match English with an apostrophe or a quote** decode the page first: `decodeEntities` (`src/testing/entities.ts`).
- **Label tables.** A table of labels keyed by a variable holds `PlainKey`s (a catalog key without placeholders; exported from
  `src/i18n`) and is read with `tKey(key)` at render, never at module scope.
- **The browser scripts.** Put the key in `src/i18n/en/client.ts` (and `es/client.ts`) with the prefix `client.` (`copy.*` keys
  in `common` count too): every such key is embedded, in the page's language, in every page's
  `<script type="application/json" id="i18n">` (the whole client catalog, a few KB; there is no per-script list). The tiny
  `static/i18n.js` reads that block before any other script and defines the global `T(key, 'English fallback')`. `app.js`,
  `desk.js`, `viewer.js`, `diagrams.js`, `editor-cm.js`, `editor-pics.js` and `graph3d.js` all load after it: write
  `const T = globalThis.T ?? ((k, en) => en ?? k);` at the top of a script that may be run without it (a test). Never
  read the block yourself. The sandboxed diagram frame has no block and no text.

### Setup texts

`setupText(slug, mcpUrl, overlay, lang)` in `src/setup/texts.ts` has an English and a Spanish text for every app (tool names, the
address and `setup: N` are identical). The setup page passes `currentLanguage()`. The rules block that Connect writes into
CLAUDE.md / AGENTS.md / GEMINI.md uses the language of the request that pressed Connect (the Language setting, else the system
locale); a tool connected in English keeps English rules until the owner presses Connect or Replace again, which rewrites the block.
Both languages are in `SETUP_HASH`; changing either raises `SETUP_VERSION`. The Claude Code plugin skill and the MCP instructions stay English.

## The "no English left" check for an area

```ts
import { enablePseudoLocale, runWithLocale } from '../i18n/core.js';
import { assertNoEnglishLeft } from '../testing/noEnglish.js';

enablePseudoLocale(true); // tests only
const out = runWithLocale('xx', () => page(t('area.title'), view(…), { nav: true }));
assertNoEnglishLeft(out, 'the inbox', { allow: [projectName, factText] });
```

Under `xx` every `t()` string comes back as `⟦…⟧`; `tHtml` wraps each run of catalog text on its own (a link inside a sentence stays
outside the brackets); and the text built from locale data (`fmt.*`, `when.ts` dates and weekdays, `localParts`, `shortDay`) is
wrapped too. The checker lists visible text outside the brackets: text nodes (including SVG `<title>` and `<text>`), the attributes
`placeholder`, `aria-label`, `title`, `alt`, `value` of `submit`/`button`/`reset` inputs (not of `<button>`, where it is a code), text-bearing `data-*`
attributes (names ending in `label`, `title`, `text`, `placeholder`, `message`, `hint`, `confirm`, `tooltip`, `alt`, and the
labels inside `data-goto`), with double quotes, single quotes or none; all HTML entities are decoded first. Script, style, code,
comments and `<pre>` are skipped; pass `{ checkPre: true }` to check `<pre>` (setup texts) once they are translated.

- Brand and product names, units and numbers are allowed (`ALLOWED_WORDS` in `src/testing/noEnglish.ts`: KB, MB, GB, TB, JSON,
  PDF, CSV, URL, MCP, OAuth, API, the browsers and systems, Docker, GitHub, Hugging Face, OpenRouter, Tailscale, Cloudflare,
  Claude, Claude Code, Codex, Cursor, OpenCode, Gemini, Gemini CLI, ChatGPT, Grok, BrainAI, Backblaze, B2, SQLite, and the other
  names the UI already shows). A multi-word entry is allowed as a phrase. Add a brand there only if it is really the same in
  Spanish.
- **Fixture data** (a project name, a fact's text, a page title the test created) is not a missed translation: pass it in
  `allow`. Only the whole phrase is removed (its single words are not allowed elsewhere), so list each fixture as it appears.
- To render a real route in `xx`, set the switch `ui_language` to `xx` in the test's store (it only means something while the
  pseudo-locale is enabled). `src/web/i18nWeb.test.ts` and `src/web/i18nHardening.test.ts` show both ways.

The parity test (`src/i18n/i18n.test.ts`) fails when a Spanish key is missing, extra, or has different placeholders; the area test
fails when a key is defined in two area files.

## Rules for the people (and agents) converting an area

1. Convert only your area's files (table below) and edit only your area's two catalog files. Never edit `index.ts` of the catalogs.
2. **Never call `t()` at module scope or inside a lazy cache** (`memoByKey`, a `const X = t(...)` at the top of a file, a table
   built once): the language is per request. Build the text inside the function that renders, or keep a table of `PlainKey`s and
   call `tKey` at render.
3. **Never decide behaviour from translated text**: not a title, a label, a status line. Compare codes, ids, kinds.
4. Watch for a local variable or parameter named `t` shadowing the imported `t` (`.filter((t) => …)`, `tags.map((t) => …)`); inside
   that function `t('key')` is a type error at best. Rename the variable.
5. Do not `t()` stored or sent text (see the top of this page).
6. Each area tests its pages **under `xx`** with `assertNoEnglishLeft` (fixtures in `allow`), and **one page per area in `es`
   through the real app** (`startTestApp`, set `ui_language` to `es`, assert a few Spanish phrases and that the lit tab and the
   back link are the same as in English).
7. English output must not change: the existing tests of your area keep passing unchanged.
8. Spanish: see the tone rules below; the same word for the same thing across areas (check `common` and the other areas' files
   before inventing a term).

## Spanish tone

- Spain Spanish, tuteo (tú): "Elige una carpeta", never "usted", never "vosotros" forms for the owner.
- Plain words, short sentences, the same tone rules as the English text: say what happened and what to do next. No
  jargon, no exclamation marks, no "por favor" in buttons.
- Buttons are verbs in the infinitive or imperative as the English is (Guardar, Reanudar, Aprobar); not "Guardar cambios"
  where English says Save.
- The product is BrainAI; keep names of other products as they are (Claude, ChatGPT, Tailscale). "Facts" are "datos",
  "Inbox" is "Bandeja", "Week" is "Semana".
- Language names are always written in their own language (English, Español), in both catalogs.
- Dates: `19 nov 2026`, 24-hour time, decimal comma (`1,2 GB`).
- Assistants' tool descriptions, server instructions and tool replies stay English.
